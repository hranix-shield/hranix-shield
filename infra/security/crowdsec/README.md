# CrowdSec — установка и учётные данные (A-11, A-29)

Питает консоль панели «Hranix Shield» **«Обнаружение вторжений»** (`ids`) — и, частично
(`crowdsec_active_bans`), консоль **«Защита периметра»** (`perimeter`). CrowdSec сам —
MIT-лицензия, поднимается **отдельным Docker-контейнером** (`docker-compose.yml` в этой
директории); процесс `server` никогда не линкует его код, только ходит к уже запущенному
Local API (LAPI) по HTTP (лицензионный гейт CLAUDE.md).

## Два разных, независимых учётных данных

CrowdSec различает **два уровня доступа** к своему LAPI — это решение самого CrowdSec, не
ограничение этого проекта:

| Учётные данные | Как заводится | Что может | Использует |
|---|---|---|---|
| **Bouncer key** (A-11) | `cscli bouncers add` | Только читать (`GET /v1/decisions`) | Чтение консоли — метрики, «Последние попытки» |
| **Machine login** (A-29) | `cscli machines add` | Читать И писать (`POST /v1/alerts`, `DELETE /v1/decisions/{id}`) | «Забанить вручную»/«Разбанить IP» |

Живьём подтверждено (см. `server/app/services/mcp/security_connectors/crowdsec.py`'s
докстринг, раздел «A-29 addendum»): bouncer-ключ, отправленный на `POST /v1/alerts`, получает
**HTTP 401** — это не баг проекта, это то, как сам CrowdSec разделяет права. Поэтому здесь
**два независимых блока** `.env`-настроек (`CROWDSEC_API_KEY` и `CROWDSEC_MACHINE_ID`/
`CROWDSEC_MACHINE_PASSWORD`) — можно иметь один, оба или ни одного; консоль честно показывает
`connector.status`/действие как `not_configured`, если нужного блока нет, никогда не
фабрикует успех.

## 1. Поднять контейнер

Не стартует автоматически вместе с приложением (тот же принцип, что и restic, A-12 — внешний
сервис, который оператор поднимает отдельно):

```sh
docker compose -f infra/security/crowdsec/docker-compose.yml up -d
```

## 2. Bouncer key (чтение, A-11) — если ещё не заведён

```sh
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli bouncers add hranix-shield-bouncer -o raw
```

Скопируйте напечатанный ключ в `.env`:

```
CROWDSEC_LAPI_URL=http://127.0.0.1:8089
CROWDSEC_API_KEY=<напечатанный ключ>
```

## 3. Machine login (запись, A-29) — новое

Требуется для того, чтобы кнопки «Забанить вручную»/«Разбанить IP» на консоли «Обнаружение
вторжений» реально работали. Пароль **генерируется случайно** — та же дисциплина, что и у
`JWT_SECRET`/`RESTIC_PASSWORD` (A-19): никогда не вписывайте фиксированную/запоминающуюся
строку.

```sh
MACHINE_PASSWORD=$(python3 -c "import secrets; print(secrets.token_urlsafe(32))")
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli machines add hranix-shield-machine --password "$MACHINE_PASSWORD" -f -
echo "CROWDSEC_MACHINE_ID=hranix-shield-machine"
echo "CROWDSEC_MACHINE_PASSWORD=$MACHINE_PASSWORD"
```

Добавьте напечатанные строки в `.env`:

```
CROWDSEC_MACHINE_ID=hranix-shield-machine
CROWDSEC_MACHINE_PASSWORD=<напечатанный пароль>
```

Проверьте, что machine появился (`Auth Type` — `password`):

```sh
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec cscli machines list
```

### Как это работает изнутри (для справки/отладки)

Коннектор (`crowdsec.py`) сам логинится через `POST /v1/watchers/login` с
`{"machine_id", "password"}`, получает короткоживущий JWT (живьём подтверждено: 1 час) и
кэширует его до истечения. Живой пример (для ручной отладки, не нужен в норме):

```sh
curl -s -X POST http://127.0.0.1:8089/v1/watchers/login \
  -H "Content-Type: application/json" \
  -d '{"machine_id":"hranix-shield-machine","password":"<пароль>"}'
# {"code":200,"expire":"2026-07-18T21:24:46Z","token":"<JWT>"}
```

## 4. «Проверить обновления»/«Применить обновления» сценариев (hub update/upgrade) — elevated `docker exec` с предпросмотром (A-45, пересматривает более раннее решение)

**История решения, честно не скрываем:** изначально (A-11/A-43) кнопка «Обновить сценарии» была
**сознательно задизейблена** — `cscli hub update` не имеет HTTP-эквивалента в LAPI (только сам
`cscli` внутри контейнера, то есть `docker exec`), а `cscli hub update`/`upgrade` тянут и
устанавливают СТОРОННИЙ код с `hub.crowdsec.net` при каждом вызове — качественно другой, более
серьёзный класс риска (supply-chain), чем точечная правка одной строки уже установленного
локального файла (раздел 6 ниже) или прямая CLI-команда над локальной БД (раздел 6.1). Это
решение **пересмотрено задачей A-45**, не отменено молча: найден реальный, официальный механизм
самого CrowdSec — `cscli hub upgrade --dry-run` («Don't install or remove anything; print the
execution plan») — который честно показывает оператору, ЧТО будет установлено, ДО того как это
установится, снимая ЧАСТЬ (не весь) риска. Полный механизм, живая проверка и остаточный риск,
который это НЕ устраняет, — раздел 6.2 ниже.

Обновить сценарии вручную (минуя панель), если нужно:

```sh
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec cscli hub update
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec cscli hub upgrade
```

## 5. «Белый список» (allowlist) — чтение через LAPI, запись через elevated docker exec (A-42/A-43/A-44)

Панель показывает реальный CrowdSec allowlist (`GET /v1/allowlists?with_content=true`) в
консоли «Обнаружение вторжений» — чтение через LAPI, запись **теперь тоже возможна**, но не
через LAPI (у него для этого физически нет HTTP-эндпоинта, см. ниже) — через elevated `docker
exec`, см. раздел 6.1. Живое исследование LAPI (перед реализацией A-42, против этого же
контейнера):

- **Чтение работает**, но нужен **machine-уровня** логин (тот же, что заведён в разделе 3
  выше) — `X-Api-Key` (bouncer, раздел 2) отвечает честным `401 {"message": "cookie token is
  empty"}`, той же формой отказа, что и у write-эндпоинтов из раздела 3.
- **Запись через LAPI НЕ работает вообще**: `POST`/`PUT`/`PATCH`/`DELETE` на `/v1/allowlists*`
  отвечают `405 Method Not Allowed` **при любых учётных данных** (проверено и вовсе без
  заголовков авторизации) — это отказ на уровне маршрутизации LAPI, не проверка прав, так что
  более сильные учётные данные это не обойдут. `cscli allowlists add/create/remove` — прямая
  операция CLI с локальной БД контейнера, HTTP-эквивалента не существует. **С A-44 это больше не
  тупик для панели** (хотя LAPI сам по-прежнему не может это сделать) — см. раздел 6.1: панель
  запускает те же `cscli` команды через elevated `docker exec`, тот же прецедент, что A-43 уже
  установила для порогов сценариев.
- Порог/длительность бана — **не читаются вообще нигде** в LAPI (`/v1/scenarios`, `/v1/hub`,
  `/v1/config` — все `404`): у CrowdSec нет единого глобального порога, каждый сценарий
  настраивается своим `leakspeed`/`capacity` в собственном YAML внутри контейнера. **С A-43 это
  больше не тупик** — панель теперь читает и меняет их напрямую через elevated `docker exec` (не
  через LAPI, у него для этого нет эндпоинта) — см. раздел 6 ниже.

Подробности и код чтения — `server/app/services/mcp/security_connectors/crowdsec.py`'s
докстринг, раздел «A-42 addendum»; запись — раздел «A-44 addendum» и раздел 6.1 ниже.

### Живая проверка чтения (ручная)

```sh
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli allowlists create test_al -d "A-42 live verification test allowlist"
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli allowlists add test_al 203.0.113.5
# ... открыть панель → «Обнаружение вторжений» → «Белый список» — должна появиться
# 203.0.113.5 с реальным комментарием. Затем обязательно убрать:
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli allowlists delete test_al
```

Автотесты: `server/tests/unit/test_crowdsec_allowlists.py` (офлайн, `httpx.MockTransport` —
и чтение, и вся матрица честных статусов), `server/tests/integration/
test_crowdsec_allowlists_live.py` (маркер `crowdsec_write_live`, самопропускается без
`CROWDSEC_MACHINE_ID`/`CROWDSEC_MACHINE_PASSWORD` — только READ-проверки: подтверждает, что
чтение реально работает и что неверный пароль честно даёт `unauthorized`). Запись из панели
теперь тестируется отдельно — см. раздел 6.1 ниже.

## 6. «Показать/изменить пороги» сценариев — elevated `docker exec` (A-43)

Единственное место в этом проекте, где `docker exec`/`docker compose restart` в СВОЙ контейнер
запускаются из работающего приложения — **узкое, явно подтверждённое оператором исключение**, не
отмена принципа «никогда docker exec» (см. `server/app/services/mcp/security_connectors/
crowdsec.py`'s докстринг, раздел «A-43 addendum», и
[docs/план-спецификация-фаза-0-порог-сценариев-2026-07-24.md](../../../docs/план-спецификация-фаза-0-порог-сценариев-2026-07-24.md)'s
«Важное архитектурное решение» — полное обоснование там, не повторяется здесь). Коротко: КАЖДЫЙ
вызов — свой разовый, НИКОГДА не кэшируемый системный запрос пароля (Touch ID/пароль macOS,
`elevated_run()`, тот же примитив A-36/A-37) — точно та же аудиторская/психологическая весомость,
что уже одобрена для `pfctl`/`netsh`-действий консоли «Периметр», применённая здесь к
`docker exec`/`docker compose restart` вместо системного файрвола.

**Почему на момент A-43 это НЕ переоткрывало «Обновить сценарии» (раздел 4 выше) — и почему это
изменилось в A-45:** на момент A-43, «Обновить сценарии» тянуло и выполняло СТОРОННИЙ код с
`hub.crowdsec.net` при каждом вызове БЕЗ какого-либо механизма предпросмотра — качественно другой,
более серьёзный класс риска (supply-chain), чем точечная `sed`-правка одной строки уже
установленного локального файла, поэтому та задача сознательно не расширяла на неё это
исключение. «Добавить в белый список» (раздел 5 выше) было на тот момент просто ДРУГОЙ, не начатой
работой (не вопрос риска) — A-44 применила этот же прецедент к allowlist, не переоткрывая вопрос
"безопасно ли это исключение вообще". **A-45 (раздел 6.2 ниже) — первый случай, когда решение по
существу ПЕРЕСМАТРИВАЕТСЯ**, а не просто применяется к новому действию: найден реальный механизм
предпросмотра (`cscli hub upgrade --dry-run`), который снимает ЧАСТЬ риска — достаточную, чтобы
теперь применить то же elevated-исключение и здесь. Риск компрометации самого
`hub.crowdsec.net` остаётся и честно описан в разделе 6.2.

**Живое исследование перед реализацией (2026-07-24, против этого же контейнера
`hranix-crowdsec`)** — таблица реальных сценариев, обоснование каждого шага дизайна (диапазон-
scoped `sed`, почему `docker` резолвится в абсолютный путь, почему у 3 из 6 файлов на самом деле
ДВА сценария, а не один) — всё в `crowdsec.py`'s докстринге, «A-43 addendum» — не дублируется
здесь во второй раз.

### Живая проверка

```sh
# Прочитать текущий порог crowdsecurity/ssh-bf прямо из файла (для сверки после теста):
docker exec hranix-crowdsec sh -c \
  "sed -n '/^name: crowdsecurity\/ssh-bf$/,/^---$/p' /etc/crowdsec/scenarios/ssh-bf.yaml"
# ... открыть панель → «Обнаружение вторжений» → «Управление» → «Показать/изменить пороги» →
# найти crowdsecurity/ssh-bf → изменить capacity 5 → 7 → «Сохранить» (запросит пароль
# администратора — реальное системное окно) → после успеха повторить sed выше и убедиться, что
# capacity: 7 реально на диске. ОБЯЗАТЕЛЬНО вернуть обратно 5 тем же путём — это боевой контейнер,
# которым пользуется весь остальной проект.
```

Автотесты: `server/tests/unit/test_crowdsec_scenario_thresholds.py` (офлайн, `elevated_run`
монкипатчится — парсинг многодокументных файлов, валидация `capacity`/`leakspeed`, sed-программа,
readback-сверка), `server/tests/integration/test_security_console_scenario_thresholds.py` (оба
новых эндпоинта, вся матрица кодов ошибок), `server/tests/regression/
test_a43_scenario_thresholds_regression.py` (честное поведение для `trigger`-сценариев, коды
`elevation_cancelled`/`elevation_failed` не схлопываются в один статус). Реальный `docker exec`
против настоящего контейнера — не автоматизировано (нет способа воспроизвести настоящий
Touch ID/пароль-диалог в CI), только эта живая проверка вручную.

## 6.1. «Добавить в белый список»/«Удалить» — elevated `docker exec` (A-44)

Применяет ТОТ ЖЕ прецедент раздела 6 (узкое, явно подтверждённое оператором исключение из
«никогда docker exec», НЕ его отмена) ко ВТОРОМУ действию — не переоткрывает вопрос, безопасно ли
это исключение вообще (см. `crowdsec.py`'s докстринг, раздел «A-44 addendum», и
[docs/план-спецификация-фаза-0-белый-список-запись-2026-07-25.md](../../../docs/план-спецификация-фаза-0-белый-список-запись-2026-07-25.md)'s
«Архитектурное решение — не переоткрывается»).

Genuinely ПРОЩЕ раздела 6: `cscli allowlists create/add/remove` — прямые CLI-команды над
отдельной фичей CrowdSec (allowlists, живой runtime-объект, перечитывается CrowdSec на каждом
запросе к LAPI), не редактирование YAML-файла руками — никакого диапазон-scoped `sed`, никакого
`docker compose restart` (в отличие от порогов сценариев, которые CrowdSec читает только при
старте контейнера).

Живьём подтверждено архитектором перед реализацией (и перепроверено разработчиком тем же путём —
прямой `docker exec`, без elevated-обёртки, только для сбора фактов, не через панель):

- `cscli allowlists create <name>` **не идемпотентна сама по себе** — повторный вызов на
  существующее имя даёт `Error: cscli allowlists create: allowlist '<name>' already exists`,
  код возврата 1. Панель распознаёт именно этот текст (shell `case` внутри elevated-скрипта) и
  трактует как «список уже есть, это нормально» — не как сбой.
- `cscli allowlists add`/`cscli allowlists remove`, наоборот, **сами по себе идемпотентны**:
  повторное добавление уже существующего значения и повторное удаление уже отсутствующего
  значения оба отвечают кодом возврата `0` (с предупреждением в тексте, не ошибкой) — живьём
  подтверждено. Панель, тем не менее, никогда не считает чистый код возврата доказательством
  результата: **обязательный отдельный readback** через уже существующий `fetch_allowlists()`
  (A-42, тот же путь чтения, не дублируется) после каждой записи — та же дисциплина, что и у
  порогов сценариев (раздел 6).
- Один именованный список-константа, `hranix_manual` — панель создаёт его лениво при первом
  добавлении, честно игнорируя «already exists», не спрашивая оператора имя списка (Фаза 0
  показывает allowlist одним плоским списком, см. раздел 5 выше).

### Живая проверка

```sh
# ... открыть панель → «Обнаружение вторжений» → «Белый список» → ввести тестовый IP (RFC 5737,
# TEST-NET, например 203.0.113.5) + комментарий → «Добавить в белый список» (запросит пароль
# администратора — реальное системное окно) → после успеха значение появляется в списке с
# реальным комментарием. Проверить напрямую:
docker exec hranix-crowdsec cscli allowlists inspect hranix_manual
# ... нажать «Удалить» на этой строке (снова запросит пароль) → значение честно пропадает из
# панели И из вывода команды выше. ОБЯЗАТЕЛЬНО убрать за собой весь тестовый список, если он был
# создан только ради этой проверки — это боевой контейнер, которым пользуется весь остальной
# проект:
docker exec hranix-crowdsec cscli allowlists delete hranix_manual
```

Автотесты: `server/tests/unit/test_crowdsec_allowlist_write.py` (офлайн, `elevated_run` И
`fetch_allowlists` монкипатчатся — валидация `value`, идемпотентный `create`-already-exists,
readback решает успех/неудачу, а не код возврата `cscli`), `server/tests/integration/
test_security_console_ids_allowlist_write.py` (оба новых эндпоинта, вся матрица кодов ошибок,
`:path`-конвертер пропускает CIDR с `/`), `server/tests/regression/
test_a44_allowlist_write_regression.py` (readback-честность в обе стороны, коды
`elevation_cancelled`/`elevation_failed` не схлопываются в один статус). Реальный `docker exec`
через elevated_run/настоящий Touch ID-диалог — не автоматизировано (та же причина, что и в
разделе 6), только живая проверка вручную выше.

## 6.2. «Проверить обновления»/«Применить обновления» сценариев — elevated `docker exec` с предпросмотром (A-45)

Применяет ТОТ ЖЕ elevated-`docker exec`-прецедент раздела 6 к третьему действию — но, в отличие
от разделов 6/6.1 (которые лишь РАСШИРЯЛИ уже принятое решение на новое действие), это первый
случай, где применение самого прецедента ранее было явно **ОТКЛОНЕНО** (раздел 4 выше, A-43) и
теперь **пересмотрено**, не просто расширено (см. `server/app/services/mcp/security_connectors/
crowdsec.py`'s докстринг, раздел «A-45 addendum», и
[docs/план-спецификация-фаза-0-обновление-сценариев-2026-07-25.md](../../../docs/план-спецификация-фаза-0-обновление-сценариев-2026-07-25.md)'s
«Пересмотр решения A-43»).

**Что изменилось:** не пароль (разовый системный пароль никогда не подтверждал, что скачанный
контент безопасен — только то, что человек нажал кнопку) — а разделение READ и APPLY на два
ОТДЕЛЬНЫХ elevated-клика:

1. **«Проверить обновления»** — `cscli hub update && cscli hub upgrade --dry-run`. `hub update`
   скачивает только `.index.json` (метаданные-каталог), `--dry-run` — официальный флаг CrowdSec
   («Don't install or remove anything; print the execution plan»), НИЧЕГО не устанавливает.
   Результат — сырой текст реального плана `cscli` (как «Правила фаервола», A-36 — не
   переизобретаем структурированный парсинг) + честный признак `has_upgrades`.
2. **«Применить обновления»** — показывается ТОЛЬКО если план не пуст. Реальный `cscli hub
   upgrade` (без `--dry-run`) + `docker compose restart crowdsec` (сценарии перечитываются
   только при старте контейнера — те же файлы, что правит раздел 6) + обязательный отдельный
   readback (`cscli hub list -o json`, честно сверяет, что `status` каждого пункта больше не
   содержит `update-available` — не просто «restart без ошибки»).

**Честно, что это НЕ устраняет:** если сам `hub.crowdsec.net` скомпрометирован, он теоретически
может отдать вредоносный «план» на шаге 1, отличающийся от того, что реально придёт на шаге 2. Ни
один локальный механизм (этот включая) не может это исключить — тот же класс остаточного риска,
что у любого пакетного менеджера (`apt`/`brew`) по отношению к своему репозиторию/индексу. Этот
механизм СНИЖАЕТ риск («оператор видит, что скачивается, до того как оно установится»), не
обнуляет его.

**Живое исследование перед реализацией (2026-07-25, против этого же контейнера
`hranix-crowdsec`)** — полная таблица live-подтверждённых форматов вывода (`Action plan:`/
`📥 download`/`🔄 check & update data files`/признак `" -> "`, `cscli hub list -o json`'s
`status: "enabled,update-available"`) — см. `crowdsec.py`'s докстринг, раздел «A-45 addendum», не
дублируется здесь во второй раз. На момент этой проверки контейнер РЕАЛЬНО имел два устаревших
пункта (`crowdsecurity/ssh-time-based-bf` 0.2→0.3, `crowdsecurity/rdns` 0.3→0.4, плюс версии двух
коллекций) — оба были установлены по-настоящему (не только dry-run) в рамках этой же проверки,
readback подтвердил 0 устаревших пунктов после, контейнер перезапущен и здоров (LAPI `/health`
отвечает 200). Оставлено в актуальном состоянии — это официальное обновление CrowdSec, не
тестовое значение для отката (в отличие от A-43/A-44's произвольных тестовых значений, у
официального апгрейда нет «исходного значения», к которому имело бы смысл возвращаться, и у
`cscli` нет команды «откатить hub» даже если бы это было нужно).

### Живая проверка

```sh
# Прочитать текущее состояние hub (для сверки после проверки в панели):
docker exec hranix-crowdsec cscli hub list -o json | python3 -c \
  "import json,sys; d=json.load(sys.stdin); [print(k,i['name'],i['status']) for k,v in d.items() for i in v if 'update-available' in i.get('status','')]"
# ... открыть панель → «Обнаружение вторжений» → «Управление» → «Проверить обновления»
# (запросит пароль администратора — реальное системное окно) → показывает реальный план ниже
# кнопки. Если план не пуст — появляется «Применить обновления»: второй клик (второй запрос
# пароля) → после успеха повторить команду выше и убедиться, что список устаревших пунктов пуст.
# Если план пуст ("Все сценарии уже актуальны") — кнопка «Применить» честно НЕ появляется, это
# правильное поведение, а не недоделанность.
```

## Живая проверка

```sh
# Забанить тестовый IP (RFC 5737 TEST-NET-1 — никогда реальный публичный адрес):
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli decisions add --ip 192.0.2.1 --duration 5m --reason "manual test"
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec cscli decisions list
# ... затем убрать:
docker compose -f infra/security/crowdsec/docker-compose.yml exec crowdsec \
  cscli decisions delete --ip 192.0.2.1
```

**Эмуляция нескольких «вторжений» разом** (для отладки/демонстрации консоли «Обнаружение
вторжений» с несколькими строками в «Последних попытках») —
[`simulate_test_bans.sh`](simulate_test_bans.sh): добавляет 4 тестовых бана (RFC 5737,
с реалистичными `--reason`, совпадающими с реально установленными сценариями) и обратный
скрипт-очистка:

```sh
sh infra/security/crowdsec/simulate_test_bans.sh          # добавить
sh infra/security/crowdsec/simulate_test_bans.sh cleanup  # убрать
```

**Честно про то, чего этот скрипт (и вся текущая настройка CrowdSec в этом проекте) не делает**:
не эмулирует реальную ДЕТЕКЦИЮ по логам — только РЕЗУЛЬТАТ детекции (уже готовое решение о бане),
подставленный напрямую через `cscli`. Автоматическая детекция по логам сейчас не подключена вообще
(`docker-compose.yml`'s `acquis.yaml` намеренно смотрит на несуществующий файл, host `/var/log` не
bind-mount'ится — осознанное архитектурное решение A-11, «валидирует только саму интеграцию с
LAPI, не превращает эту машину в защищённый хост»). Подключение реальной детекции (например,
SSH-логов) — отдельное решение о безопасности хоста, не часть этого скрипта.

Автотесты: `server/tests/unit/test_crowdsec_write_client.py` (офлайн, `httpx.MockTransport`),
`server/tests/integration/test_crowdsec_write_live.py` (маркер `crowdsec_write_live`,
самопропускается без `CROWDSEC_MACHINE_ID`/`CROWDSEC_MACHINE_PASSWORD` — банит/разбанивает
`192.0.2.1` и всегда убирает бан за собой).
