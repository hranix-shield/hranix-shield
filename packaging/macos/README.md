# Hranix Shield — сборка и установка на macOS (A-20)

Нативный установщик macOS для Hranix Shield («Панель безопасности», Фаза 0) — решает
архитектурный разрыв, из-за которого Docker-развёртывание никогда не видит настоящий хост
пользователя для консоли «Периметр» (`os_firewall`/`os_disk_encryption` внутри контейнера всегда
видят Linux-контейнер, не macOS/Windows хост — см.
[план-спецификацию](../../docs/план-спецификация-фаза-0-нативные-установщики-2026-07-17.md)).

## Что тут есть

- `hranix_shield_app.py` — точка входа: `rumps`-обвязка (иконка в строке меню, без окна/Dock).
- `hranix-shield.spec` — PyInstaller-спека, собирающая `.app` (onedir).
- `dist/Hranix Shield.app` / `dist/Hranix Shield.dmg` — результат сборки (не коммитятся в git —
  собираются локально, см. ниже).

Бизнес-логика запуска (миграции → uvicorn в фоновом потоке → ожидание `/health` → открытие
браузера) живёт в `server/launcher.py`, общем для всех трёх ОС (A-20 macOS, будущие A-21 Windows/
A-22 Linux переиспользуют его без изменений) — этот каталог содержит только macOS-специфичную
упаковку вокруг него.

## Сборка

Нужен **отдельный, лёгкий** build-venv — не общий dev-`server/venv` (тот тянет
`server/requirements.txt` целиком, включая Фаза-2/голос-зависимости, torch и так далее, ненужные
и нежелательные в поставляемом бинарнике):

```bash
python3.12 -m venv /tmp/hranix-build-venv
/tmp/hranix-build-venv/bin/pip install -r server/requirements-packaged.txt

./packaging/macos/vendor-osquery.sh    # A-24: -> packaging/macos/vendor/osquery/osqueryi (run once first)

/tmp/hranix-build-venv/bin/pyinstaller packaging/macos/hranix-shield.spec \
    --distpath packaging/macos/dist --workpath packaging/macos/build --noconfirm
```

Результат: `packaging/macos/dist/Hranix Shield.app`.

**Собрано и проверено на:** macOS 26.5.2, Apple Silicon (arm64), Python 3.12.13, PyInstaller
6.21.0. Кросс-архитектурная сборка (Intel/x86_64 или `universal2`) не производилась и не
проверялась — PyInstaller не кросс-компилирует между архитектурами так же, как не
кросс-компилирует между ОС; для Intel-Mac нужна отдельная сборка на Intel-машине (или `arch -x86_64`
на Apple Silicon с Rosetta — не опробовано в этой задаче).

### `.dmg`

```bash
mkdir -p /tmp/dmg-staging
cp -R "packaging/macos/dist/Hranix Shield.app" /tmp/dmg-staging/
ln -s /Applications /tmp/dmg-staging/Applications
hdiutil create -volname "Hranix Shield" -srcfolder /tmp/dmg-staging -ov -format UDZO \
    "packaging/macos/dist/Hranix Shield.dmg"
rm -rf /tmp/dmg-staging
```

Стандартный drag-to-`Applications` образ (иконка `.app` + симлинк на `/Applications` в корне
смонтированного тома). Собран и проверен (`hdiutil attach -readonly`, содержимое подтверждено) —
без кастомного фона/расположения иконок (не в скоупе DoD этой задачи).

## onedir vs onefile — решение и почему

**Выбран onedir** (`COLLECT` + `BUNDLE` в `.spec`), не onefile. Изначально план оставлял это на
усмотрение реализации с оговоркой «эмпирически сравнить, зафиксировать выбор» — сравнение
проведено, и результат оказался однозначным сразу по двум независимым основаниям:

1. **Сам PyInstaller 6.21.0 явно предупреждает при попытке собрать onefile + `.app`-бандл
   (windowed-режим для macOS):**
   ```
   DEPRECATION: Onefile mode in combination with macOS .app bundles (windowed mode) don't make
   sense (a .app bundle can not be a single file) and clashes with macOS's security. Please
   migrate to onedir mode. This will become an error in v7.0.
   ```
   Это не домысел архитектора — дословный вывод инструмента сборки, авторитетнее любого
   стороннего рассуждения об onedir-vs-onefile trade-off.

2. **Эмпирически onefile-вариант реально не запустился.** Собран experimental onefile-`.spec`
   (тот же entry point/datas/hiddenimports, `exclude_binaries=False`, `BUNDLE(exe, ...)` напрямую
   без `COLLECT`) — при запуске:
   ```
   [PYI-98250:ERROR] Failed to load Python shared library '/tmp/_MEITZllAQ/Python': dlopen(...):
   tried: '/tmp/_MEITZllAQ/Python' (no such file), ...
   ```
   Самораспаковка во временный каталог при каждом запуске (главный практический минус onefile,
   упомянутый в задании — задержка старта у сервера, который и так поднимает БД/миграции) здесь
   даже не успела стать проблемой: связка onefile+`.app`+PyObjC/`rumps` не находит собственную
   распакованную `Python`-библиотеку и падает на старте. onedir-сборка запускалась и проходила
   полный DoD-прогон (см. ниже) без единой похожей ошибки.

Экспериментальные onefile-артефакты (spec/build/dist) удалены после проверки — не входят в
финальную поставку, в репозитории остаётся только onedir-путь.

## Первый запуск / конфигурация

Первый запуск создаёт каталог данных через `platformdirs` (см. `server/app/config.py`'s A-19
`is_packaged()`/`_packaged_data_dir()`):

```
~/Library/Application Support/Hranix Shield/   # data/, .jwt_secret, .restic_password, config.env
~/Library/Logs/Hranix Shield/                  # assistant.log
```

Перед первым запуском (или после — но `BOOTSTRAP_ADMIN_*` читается один раз, пока в `users` нет ни
одной записи) положите `config.env` в первый из путей выше — тот же формат `KEY=VALUE`, что и
корневой `.env.example` проекта:

```bash
mkdir -p "$HOME/Library/Application Support/Hranix Shield"
cat > "$HOME/Library/Application Support/Hranix Shield/config.env" << 'EOF'
SERVER_PORT=8080
BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=<замените>

# Docker-компаньоны (CrowdSec/ClamAV/Wazuh) — те же контейнеры, что в
# infra/security/*/docker-compose.yml, опубликованные на 127.0.0.1 — .app
# запущен нативно на хосте, поэтому видит их так же, как venv-режим (не
# `hranix-crowdsec`/`hranix-clamav` по имени контейнера — это для случая,
# когда САМ Hranix Shield тоже в Docker, что не относится к этой сборке).
CROWDSEC_LAPI_URL=http://127.0.0.1:8089
CROWDSEC_API_KEY=<см. cscli bouncers add>
CLAMAV_ENABLED=True
WAZUH_API_URL=http://127.0.0.1:55000
WAZUH_API_USERNAME=wazuh-wui
WAZUH_API_PASSWORD=<из infra/security/wazuh/.env>
EOF
```

Без `config.env` сервер стартует с дефолтами `Settings` (см. `server/app/config.py`) — панель и
`/health` работают, но `BOOTSTRAP_ADMIN_*` не заданы (никакого администратора создано не будет —
вход будет невозможен, пока пользователь не задаст эти переменные и не перезапустит) и коннекторы
CrowdSec/ClamAV/Wazuh честно показывают `not_configured`/выключены.

## Gatekeeper: «неизвестный разработчик»

Бинарник **не подписан и не нотаризован** — осознанное решение этой фазы (подпись кода вне
скоупа A-20, см. план-спецификацию). При первом запуске (двойной клик, или открытие `.app` из
смонтированного `.dmg`) macOS Gatekeeper покажет предупреждение о неизвестном разработчике и
не даст открыть приложение обычным двойным кликом.

**Обход (стандартный для несигнированных `.app` на macOS):**
1. Правый клик (или Control+клик) на `Hranix Shield.app` → **Открыть**.
2. В появившемся диалоге снова нажать **Открыть** (в этот раз с опцией "всё равно открыть").
3. Дальше приложение запускается обычным двойным кликом без повторных предупреждений.

Это трение реально существует и не скрывается: пользователю придётся сделать этот шаг один раз
при первой установке.

## osquery включён в установку из коробки (A-24)

Консоли **«Сеть»** и **«Вирусная активность»** (осquery-часть) теперь работают сразу после
установки — конечному пользователю НЕ нужно самому ставить `brew install --cask osquery`
(это по-прежнему возможно и поддерживается как fallback, см. ниже, но больше не обязательно).

**Как это устроено:** `packaging/macos/vendor-osquery.sh` скачивает официальный `.pkg` osquery
(https://github.com/osquery/osquery/releases — см. лицензии ниже для точной версии/ссылки/
sha256), извлекает его без установки в систему (`pkgutil --expand-full`), достаёт реальный
Mach-O бинарник `osqueryd` из `opt/osquery/lib/osquery.app/Contents/MacOS/osqueryd` (в
официальном `.pkg` `osqueryi` — это символическая ссылка на тот же самый исполняемый файл;
osquery — один бинарник, переключающий поведение демон/интерактивная-оболочка по имени, под
которым он запущен, подтверждено эмпирически) и кладёт копию под именем `osqueryi` в
`packaging/macos/vendor/osquery/` (не коммитится в git — большой бинарный артефакт,
воспроизводимый скриптом, см. `.gitignore`).

**Код-подпись — единственная нетривиальная часть.** Оригинальная подпись Apple на `osqueryd`
— это подпись APP-BUNDLE'а (её "Sealed Resources" ссылается на соседние файлы внутри
`Contents/Resources`/`Contents/Info.plist`, которых больше нет рядом с вынесенной копией) —
подтверждено эмпирически, что запуск скопированного, но всё ещё исходно подписанного бинарника
напрямую **убивается ядром** (`exit 137`, SIGKILL, без единой строки вывода) на этой машине с
Apple Silicon: macOS требует у КАЖДОГО исполняемого Mach-O валидную подпись, а
app-bundle-подпись с отсутствующими sealed-ресурсами невалидна как отдельный файл. Исправление
(`vendor-osquery.sh`): снять оригинальную подпись и переподписать **ad hoc**
(`codesign --sign -`) — такая подпись покрывает только сам файл, без ссылок на соседние
ресурсы, и запускается локально без необходимости в доверенном сертификате (сам `.app` этого
проекта и так не подписан/не нотаризован, см. ниже — вшитый ad hoc-подписанный бинарник не
добавляет новых требований к доверию).

`hranix-shield.spec` подключает вшитый бинарник через `datas=[...]` (не `binaries=[...]` —
см. комментарий в самом `.spec`-файле: это самостоятельный исполняемый файл, вызываемый только
через subprocess, а не Python-расширение, которое `binaries` предназначен обслуживать).
PyInstaller всё равно сам переклассифицировал его во внутреннюю категорию "binary" (по магическим
байтам Mach-O, не по тому, в каком списке файл был объявлен) и во время сборки `.app`
дополнительно **утончил** его до `arm64`-only и **переподписал** в рамках общего подписания
всего бандла — подтверждено эмпирически: собранная копия внутри `.app`
(`Contents/Resources/vendor/osquery/osqueryi`, символическая ссылка на
`Contents/Frameworks/vendor/osquery/osqueryi` — то же соглашение macOS BUNDLE, что и для любого
другого нативного бинарника в этой сборке) по-прежнему имеет валидную ad hoc-подпись и реально
запускается.

`osquery.py`'s `_resolve_osqueryi()` (A-24) в упакованном режиме (`is_packaged()`, A-19) сначала
проверяет вшитый бинарник рядом с приложением (`sys._MEIPASS/vendor/osquery/osqueryi`), и только
если его там нет — падает обратно на `osqueryi`, резолвимый через системный `PATH` (dev/Docker/
venv-режим, где разработчик мог поставить osquery вручную сам, как раньше) — это поведение НЕ
удалено, только стало вторым приоритетом.

**Живая проверка (2026-07-18):** на этой машине разработки `osqueryi` НЕ установлен через brew
(`which osqueryi` → not found, подтверждено перед началом и после). Собранный `.app` с вшитым
osquery запущен на изолированном порту 8091, с изолированным `$HOME` (чтобы не задеть реальный
установленный пользователем `.app` на порту 8080) — `GET /security/consoles/network` и
`GET /security/consoles/av` оба вернули `connector`/`connectors.osquery` со `status: "ok"` и
реальные данные этого хоста (например, `active_connections: 30` с реальными процессами вроде
"Notes"/"Code Helper"/"Python" и их реальными remote-адресами; `osquery_process_count: 875`).
Прямой вызов вшитого бинарника вручную (`.../vendor/osquery/osqueryi --json "SELECT count(*)
FROM processes;"`) дал близкое число (872 — расхождение в единицы объясняется тем, что два
вызова не одновременны, на живой системе число процессов меняется от секунды к секунде) —
подтверждает, что API реально использует вшитый бинарник, а не выдумывает ответ.

## A-25: настоящий нативный агент Wazuh (не «manager следит сам за собой»)

**Проблема, которую это решает:** до A-25 консоль «Журналы ОС» на нативной установке показывала
записи о файлах ВНУТРИ Docker-контейнера Wazuh Manager (`/monitored/data/assistant.db` и т.п. —
путь, который видит только сам Manager, см. `infra/security/wazuh/docker-compose.yml`'s Decision
#2), а не о реальных файлах этой установки (`~/Library/Application Support/Hranix Shield/...`).
Причина: Manager был единственным «агентом» (id `"000"`, сам себя мониторит) — никакого настоящего
агента на хосте не существовало, и порты энролмента (1514/1515) сознательно не публиковались
(A-16's Decision #1, 2026-07-16, host-safety). A-25 (2026-07-18) — явный пересмотр архитектора
этого решения: см. `infra/security/wazuh/docker-compose.yml`'s "Decision #3" — 1514/1515
опубликованы на `127.0.0.1` (не `0.0.0.0`), теперь у них есть легитимный клиент: нативный агент
этой же установки.

### Архитектурная развилка (а)/(б) — выбран (б)

Задание явно требовало решить и не оставлять половинчатым:

- **(а)** — заменить весь `.dmg`-пайплайн на `.pkg`+`pkgbuild`/`productbuild`, ставящий и сам
  продукт, и агент Wazuh одним установщиком.
- **(б)** — оставить A-20's `.dmg`-пайплайн полностью как есть; сам `.app` при ПЕРВОМ запуске
  (не при каждом) проверяет наличие агента и, если отсутствует, один раз показывает системный
  диалог (`rumps.alert`) с предложением установить его; при согласии — скачивает официальный
  `.pkg` с `packages.wazuh.com` и ставит его через `osascript ... with administrator privileges`
  (тот же стандартный, видимый пользователю системный запрос прав, что macOS показывает для любого
  административного действия — не тихая эскалация в фоне).

**Выбрано (б)**, по трём причинам (подробно — в `wazuh_agent_setup.py`'s docstring):
1. не переоткрывает уже собранный и задокументированный `.dmg`/onedir-пайплайн A-20 (onedir-vs-
   onefile исследование, обход Gatekeeper и т.д.) — (а) сделало бы всё это бессмысленным ради
   задачи, которая не про сам продукт-инсталлятор;
2. разделяет «поставить Hranix Shield» и «поставить постоянную системную GPLv2-службу
   EDR-агента» — пользователь, который не хочет второго, может отказаться в диалоге, не блокируя
   базовый продукт (единый `.pkg`, вариант (а), сделал бы агент обязательным шлюзом перед ВСЕЙ
   установкой — решение продукта большего масштаба, чем эта задача);
3. совпадает с принципом «видимый, разовый, стандартный системный запрос — никогда тихая фоновая
   эскалация», уже применённым everywhere в проекте (CLAUDE.md, A-18).

### Что реально происходит (см. `wazuh_agent_setup.py`)

1. Первый запуск: `is_agent_installed()` проверяет `/Library/Ossec/bin/wazuh-control`; если это уже
   первый ПОСЛЕ прошлого решения запуск (маркер `.wazuh_agent_prompted` в каталоге данных, A-19),
   ничего не спрашивается повторно.
2. При согласии — на фоновом потоке (чтобы не блокировать `rumps`' event loop и появление иконки):
   - скачивает официальный `.pkg` (https://packages.wazuh.com/4.x/macos/wazuh-agent-4.14.6-1.<arch>.pkg
     — версия **зафиксирована на 4.14.6, совпадает с версией Manager-образа**
     `infra/security/wazuh/docker-compose.yml`'s `wazuh/wazuh-manager:4.14.6`, Wazuh сам
     рекомендует совпадение версий агент/manager);
   - пишет `/tmp/wazuh_envs` (`WAZUH_MANAGER`/`WAZUH_REGISTRATION_SERVER`/`WAZUH_AGENT_NAME` —
     официальный, задокументированный на documentation.wazuh.com механизм авто-конфигурации при
     установке, НЕ настоящая переменная окружения, а маркер-файл по фиксированному пути);
   - одним `osascript ... with administrator privileges` (один системный запрос пароля) выполняет:
     `installer -pkg ... -target /` → правит СОБСТВЕННЫЙ `ossec.conf` агента
     (`/Library/Ossec/etc/ossec.conf` — НЕ manager'а, два разных файла с одним именем) через `sed`,
     добавляя `<syscheck><directories>` на реальные platformdirs-каталоги (`_data_dir()`/
     `platformdirs.user_log_dir(...)`, A-19) → `launchctl bootstrap system
     /Library/LaunchDaemons/com.wazuh.agent.plist` (первый старт демона — по документации это
     отдельный шаг после `installer`, не автоматический).
   - Первый старт демона = автоматический энролмент через `authd` (порт 1515, `<enrollment>`
     включён в конфиге агента по умолчанию — подтверждено живьём, см. отчёт задачи) — Wazuh сам
     присваивает новый numeric id, отличный от `"000"`.
   - После установки запрашивает у Manager (`WazuhClient.get_agent_id_by_name`, новый метод,
     добавлен этой же задачей) id только что созданного агента по имени
     (`hranix-shield-<hostname>`) и сохраняет его в `config.env` как `WAZUH_AGENT_ID=<id>`
     (`upsert_config_env`, сохраняет остальные строки как есть) — `Settings.wazuh_agent_id`
     ничего не пришлось перепрошивать: pydantic-settings уже читает `WAZUH_AGENT_ID` из
     `config.env`/окружения без единой правки `config.py`/`wazuh.py` (кроме нового метода
     `get_agent_id_by_name` — единственная правка `wazuh.py`, отдельным коммитом).

### Резолвинг HOME для системной службы (важный вопрос из задания)

Агент Wazuh на macOS — это `launchd`-демон в `system`-домене (`/Library/LaunchDaemons/...`), а не
что-то, привязанное к сессии залогиненного пользователя — он работает от `root`, без собственного
понятия «домашний каталог залогиненного человека» в духе `$HOME`. Поэтому `<syscheck><directories>`
в его конфиге **не может** ссылаться на `$HOME` символически — это должен быть уже полностью
резолвленный, абсолютный путь. Именно поэтому `build_privileged_setup_script()` вычисляет
`platformdirs.user_data_dir(...)`/`user_log_dir(...)` **заранее, на стороне вызывающего процесса**
(`hranix_shield_app.py`, который выполняется от залогиненного пользователя — это ОН знает свой
`$HOME`), и подставляет уже готовую абсолютную строку в генерируемый bash-скрипт — агенту-демону
никогда не приходится самому резолвить чей-то `$HOME`.

### Честная граница проверки в этой сессии

**Реально проверено живьём (см. отчёт задачи A-25 для точных команд/вывода):**
- `infra/security/wazuh/docker-compose.yml`'s новые порты 1514/1515 реально слушают на
  `127.0.0.1` этой самой машины (`nc -zv`).
- Официальный `.pkg` реально скачивается с `packages.wazuh.com`, подписан и нотаризован Wazuh Inc
  (`pkgutil --check-signature`) — не подделка, не битый файл.
- Весь механизм энролмента+FIM (тот же `authd`/`agent-auth`, та же версия 4.14.6) подтверждён
  живьём — но на РЕАЛЬНОМ Linux-агенте внутри одноразового тестового контейнера на этой же машине
  (та же честная граница, что для A-22/A-24), не на настоящем macOS-хосте: новый agent id (не
  `"000"`), статус `active`, и настоящее FIM-событие про файл в каталоге, ИМИТИРУЮЩЕМ реальный
  platformdirs-путь этого продукта.
- Логика `wazuh_agent_setup.py` целиком (выбор архитектуры, маркер, upsert `config.env`, парсинг
  `manager_host`, и — эмпирически — сам сгенерированный bash/`sed`-скрипт, реально прогнанный
  против синтетического `ossec.conf`) — юнит-тестами, `packaging/macos/test/
  test_wazuh_agent_setup.py`.
- Пересобранный `.app` (с этим новым модулем) реально запускается на этой машине без ошибок
  импорта, поднимает панель, отвечает на `/health`.

**НЕ проверено живьём на этой машине, честно (принцип 8):** фактическая установка официального
Wazuh-агента КАК СИСТЕМНОЙ СЛУЖБЫ на этот настоящий Mac — `installer -pkg ... -target /` и
`launchctl bootstrap system ...` оба требуют root, а `osascript ... with administrator privileges`
показывает НАСТОЯЩИЙ системный диалог, ожидающий, что живой человек введёт пароль администратора
за этим же экраном прямо сейчас — у автоматической сессии разработчика такой возможности нет (тот
же класс ограничения, что «нет Windows-машины» у A-21, только здесь машина есть, а интерактивного
человека за паролем — нет в эту сессию). **Первый реальный запуск пересобранного `.app` живым
пользователем на этой машине — единственный оставшийся шаг, чтобы увидеть настоящий agent id и
настоящее FIM-событие про `~/Library/Application Support/Hranix Shield/...` собственными глазами.**

## Известные ограничения / что честно не проверено

- **Только Apple Silicon (arm64).** Не собрано и не проверено на Intel Mac. Вшитый `osqueryi`
  также утончается PyInstaller'ом до `arm64`-only при сборке (см. выше) — на гипотетической
  Intel-сборке потребовалась бы отдельная проверка, что универсальный `.pkg`'s x86_64-срез тоже
  корректно извлекается/утоньшается.
- Код-подпись/нотаризация самого `.app` не делались (осознанно, вне скоупа) — см. отдельно
  описанный ad hoc-codesign именно для вшитого `osqueryi`, выше, это другой, более узкий вопрос.
