# Hranix Shield — сборка и установка на Windows (A-21)

Нативный установщик Windows для Hranix Shield («Панель безопасности», Фаза 0) — решает тот же
архитектурный разрыв, что и [macOS-установщик (A-20)](../macos/README.md) и
[Linux-установщик (A-22)](../linux/README.md): Docker-развёртывание никогда не видит настоящий
хост пользователя для консоли «Периметр» (`os_firewall`/`os_disk_encryption` внутри контейнера
всегда видят Linux-контейнер, не хост — см.
[план-спецификацию](../../docs/план-спецификация-фаза-0-нативные-установщики-2026-07-17.md)).

## Важное отличие от A-20/A-22: писалось и проверялось БЕЗ Windows-машины

Среда разработки этой задачи — macOS. PyInstaller принципиально не кросс-компилирует (официальная
позиция проекта: собирать нужно на целевой ОС), и Inno Setup's компилятор (`ISCC.exe`) сам по себе
исполняется только на Windows. **Единственный способ реально собрать и проверить этот установщик —
через `.github/workflows/windows-build.yml` на настоящем `windows-latest`-раннере GitHub Actions**
— пользователь явно выбрал этот путь вместо «написать вслепую без проверки» (см. историю решения в
план-спецификации A-21). Всё в этом каталоге написано и синтаксически проверено (см. ниже), но
**ни разу не собиралось и не запускалось живьём в этой сессии** — первый реальный прогон произойдёт
только когда архитектор запушит код в GitHub.

## Что тут есть

- `hranix_shield_tray.py` — точка входа: `infi.systray`-обвязка (иконка в области уведомлений, без
  окна/консоли).
- `hranix-shield.spec` — PyInstaller-спека, собирающая onedir-бандл.
- `installer.iss` — Inno Setup script, собирающий `hranix-shield-setup.exe`.
- `test/check_tray_locale.py` — автономная (не упакованная) проверка риска кодирования кириллицы
  в `infi.systray` (см. ниже) — запускается воркфлоу, не входит в сам собранный установщик.
- `dist/` — результат сборки (не коммитится, см. корневой `.gitignore`'s `packaging/*/dist/`).

Бизнес-логика запуска (миграции → uvicorn в фоновом потоке → ожидание `/health` → открытие
браузера) живёт в `server/launcher.py`, общем для всех трёх ОС (A-20 macOS и A-22 Linux уже
используют его без изменений, эта задача переиспользует его как есть, ничего в нём не меняя) —
этот каталог содержит только Windows-специфичную упаковку вокруг него.

## Архитекторское решение: tray-иконка, не Windows NT-служба

В отличие от Linux (A-22 — headless-сервер, поэтому systemd system-service от выделенного
пользователя), Windows-сборка нацелена на персональный ноутбук нетехнического руководителя — та же
аудитория и модель, что у macOS (A-20 — menu-bar иконка через `rumps`). Полноценный NT-сервис
(`pywin32`'s `win32serviceutil`, интеграция с Service Control Manager/Event Log, отдельный
installer-шаг регистрации службы) сложнее и не даёт ничего нужного этой аудитории — решение
принято архитектором заранее, не переоткрывалось в этом прогоне. Используется **`infi.systray`**
(иконка в трее) + **`Pillow`** (рендер иконки — сохраняется как реальный `.ico`-файл во временный
каталог при каждом запуске, `infi.systray` не принимает изображение в памяти, в отличие от
изначально использованного `pystray` — см. "Замена библиотеки трея" ниже и
`hranix_shield_tray.py`'s `_generate_icon_file()`).

## Замена библиотеки трея: `pystray` → `infi.systray` (лицензионная находка)

Первая версия этого файла использовала `pystray==0.19.5`. При лицензионной сверке (тот же порядок,
что и для всех остальных зависимостей упаковки) выяснилось, что `pystray` — **LGPLv3**, не
MIT/Apache/BSD, как остальные пакующие зависимости (`rumps`, `platformdirs`). Находка поднята
архитектору, эскалирована пользователю, который решил **заменить библиотеку**, а не запрашивать
отдельное согласование на LGPL-исключение. Заменена на **`infi.systray==0.1.12.1` (BSD-3-Clause)** —
см. таблицу лицензий ниже.

Замена библиотеки повлекла три содержательных отличия в `hranix_shield_tray.py` (подробно
задокументированы в докстринге самого файла):

1. **`SysTrayIcon`'s `icon` — путь к реальному `.ico`-файлу на диске**, не `PIL.Image` в памяти
   (`pystray` принимал именно объект в памяти). `_generate_icon_file()` рисует тот же щит+"H", но
   сохраняет в реальный файл во временном каталоге (`tempfile.gettempdir()`), перегенерируется на
   каждом запуске — Pillow поэтому **остаётся** зависимостью (проверено `grep`, не предположено, что
   больше нигде в проекте не используется), просто с другой ролью.
2. **`SysTrayIcon.start()` не блокирует вызывающий поток** (в отличие от `pystray.Icon.run()`) — он
   поднимает Win32-message-loop в отдельном потоке и сразу возвращает управление. `main()` теперь
   ждёт на `threading.Event`, который выставляет `on_quit`-колбэк — тот же паттерн, что уже
   используется в `packaging/linux/hranix_shield_service.py`'s `_shutdown_requested` (там его
   выставляет обработчик SIGTERM/SIGINT, здесь — колбэк `infi.systray`).
3. **`infi.systray==0.1.12.1` безусловно добавляет свой собственный пункт меню `('Quit', None,
   SysTrayIcon.QUIT)`** — захардкожен, по-английски, нет параметра конструктора, чтобы это подавить
   или переименовать (проверено чтением `traybar.py`, не предположено). Собственный пункт "Выход"
   этого файла добавляется **вместе** с этим, не вместо — реальное меню покажет ОБА пункта ("Выход"
   и "Quit"), оба рабочие (оба вызывают одинаковый `DestroyWindow` → `on_quit(...)` путь). Косметическая,
   неизбежная в этой версии библиотеки особенность, не баг этого файла.

## Сборка — ТОЛЬКО через CI (`.github/workflows/windows-build.yml`)

Полный пайплайн на `windows-latest`:

1. `actions/setup-python@v5` → Python 3.12.
2. Лёгкий build-venv, `pip install -r server/requirements-packaged.txt` (НЕ полный dev
   `server/requirements.txt` — та же экономия, что уже сделана для macOS/Linux).
3. **Проверяет, что `infi.systray` не падает с исключением на кириллических подписях меню под
   локалью этого раннера** (`test/check_tray_locale.py`, см. "Кириллица в трее" ниже) — до сборки
   PyInstaller-бандла, чтобы упасть быстро и дёшево, если сама библиотека трея не заведётся на этом
   раннере вообще.
4. **(A-24) Вшивает osquery**: скачивает официальный `osquery-5.23.1.msi`, проверяет его sha256,
   извлекает `osqueryi.exe` через `msiexec /a ... /qn TARGETDIR=...` (административная установка —
   без реальной инсталляции в систему раннера), кладёт в
   `packaging\windows\vendor\osquery\osqueryi.exe`, и сразу проверяет, что извлечённый файл реально
   запускается и отвечает на настоящий JSON-запрос — см. "osquery включён из коробки" ниже.
5. `pyinstaller packaging/windows/hranix-shield.spec --distpath packaging/windows/dist
   --workpath packaging/windows/build --noconfirm` → `packaging/windows/dist/Hranix Shield/`
   (включая вшитый `vendor/osquery/osqueryi.exe` из шага 4, см. `hranix-shield.spec`'s
   `datas=[...]`).
6. Находит (или ставит через choco, если раннер вдруг без него) `ISCC.exe`, компилирует
   `installer.iss` → `packaging/windows/dist/installer/hranix-shield-setup.exe`.
7. Пишет `config.env` с bootstrap-админом в `%LOCALAPPDATA%\Hranix\Hranix Shield\config.env`
   (см. ниже "Первый запуск") **до** первого запуска установленного бинарника.
8. Ставит `.exe`-инсталлятор тихо: `/VERYSILENT /SUPPRESSMSGBOX /NORESTART`.
9. Запускает установленный `Hranix Shield.exe` отдельным шагом, поллит `/health` до 200
   (таймаут 60с, не `sleep`).
10. Проверяет вход под bootstrap-админом: `POST /auth/login` → реальный JWT в ответе.
11. **Сверяет консоль «Периметр» с `netsh advfirewall show allprofiles` этой же машины** — тот же
    протокол, что архитектор просил ("сравнить ответ `GET /security/consoles/perimeter` с `netsh
    advfirewall show allprofiles state` на самом раннере"): шаг запускает ровно ту же команду,
    что и сам коннектор (`os_firewall.py`'s `_windows_firewall_active()`), парсит `State ON/OFF` по
    профилям и падает, если API отвечает не так же, как реальный `netsh` этой машины — но только
    когда `connector.status == "ok"` (иначе это другая, отдельно фиксируемая находка, не повод
    молча пропускать проверку **и** не повод её проваливать).
12. **(A-24) Сверяет консоли «Сеть»/«Вирусная активность» с прямым вызовом вшитого
    `osqueryi.exe`** — в отличие от шага 11, здесь `connector.status == "ok"` утверждается БЕЗ
    условия (после A-24 у раннера нет честной причины отвечать иначе), и дополнительно сравнивает
    `osquery_process_count` консоли `av` с прямым вызовом того же самого вшитого бинарника
    (допуская обычный дрейф числа процессов между двумя неодновременными снимками, не требуя
    побайтового совпадения) — см. "osquery включён из коробки" ниже.
13. Останавливает процесс (`Stop-Process -Force` — жёсткое завершение, НЕ проверка
    graceful-shutdown; A-22's Linux-проверка `systemctl stop` → SIGTERM → `handle.stop()` не имеет
    прямого аналога здесь: у tray-приложения нет удалённо вызываемого "нажать Выход" из CI-скрипта,
    и у Windows GUI-процессов нет SIGTERM-эквивалента, который можно послать снаружи так же, как
    `kill`/`systemctl stop` на Linux — честно не заявляется как эквивалентная проверка).
14. Загружает собранный установщик как workflow-артефакт.

Полный текст: [`.github/workflows/windows-build.yml`](../../.github/workflows/windows-build.yml).

## osquery включён в установку из коробки (A-24)

Консоли **«Сеть»** и **«Вирусная активность»** (osquery-часть) должны работать сразу после
установки — конечному пользователю не нужно самому ставить MSI с
osquery.io/downloads/official/ (`infra/security/osquery/README.md`'s инструкция остаётся
fallback-документацией для Docker/venv-режима разработки). Написано и синтаксически
провалидировано (`actionlint` — ноль замечаний по обновлённому workflow), но **НЕ проверено
живьём в этой сессии** — та же честная граница, что и у всего остального в этом каталоге (нет
доступа к реальной Windows-машине/GitHub Actions отсюда, см. DoD ниже).

**Как это устроено:** workflow'а собственный шаг "Vendor osquery" скачивает официальный
`osquery-5.23.1.msi`, сверяет его sha256, извлекает содержимое через `msiexec /a osquery.msi /qn
TARGETDIR=...` (административная установка — стандартный Windows-приём получить файлы MSI без
реальной установки в систему) и копирует `osqueryi.exe` в
`packaging\windows\vendor\osquery\osqueryi.exe`. В отличие от macOS/Linux, официальный Windows
MSI хранит `osqueryi.exe` как отдельный, самостоятельный PE32+-файл (не символическую
ссылку/переименованную копию `osqueryd.exe` — оба реально разные файлы) — подтверждено на этой
macOS-машине разработки независимым инструментом `msitools`' `msiextract` (не самим `msiexec`,
которого на macOS нет; окончательное доказательство даст только реальный прогон на
`windows-latest`, см. DoD), поэтому шаг для Windows проще, чем macOS-скрипт: не нужно ни
переименование, ни ad hoc-codesign — Windows не требует подписи для запуска локального `.exe`.

`hranix-shield.spec` подключает `vendor/osquery/osqueryi.exe` через `datas=[...]` (та же
логика/комментарий, что в macOS/Linux-спеках); `installer.iss`'s единственная строка `[Files]`
(рекурсивный wildcard по всему `dist\Hranix Shield\`) уже покрывает его без отдельной записи.
`osquery.py`'s `_resolve_osqueryi()` (A-24) ищет вшитый `osqueryi.exe` по тому же пути
(`sys._MEIPASS\vendor\osquery\osqueryi.exe`) на `sys.platform == "win32"`, падая обратно на
`osqueryi`/`PATH` при его отсутствии — то же поведение, что и на двух других ОС.

### Почему `%LOCALAPPDATA%`, не `%APPDATA%`

Task-брифинг этой задачи предполагал `%APPDATA%\Hranix\Hranix Shield\config.env` — проверено по
исходнику `platformdirs==4.10.0`'s `windows.py` (не по памяти, 2026-07-18):
`user_data_dir(appname, appauthor)` по умолчанию вызывается с `roaming=False`
(`app/config.py`'s `_packaged_data_dir()` не передаёт `roaming=True`), что резолвится через
`CSIDL_LOCAL_APPDATA`, то есть **`%LOCALAPPDATA%`**, не роуминговый `%APPDATA%`. Воркфлоу и этот
README используют реально проверенный путь, не предположенный.

## Первый запуск / конфигурация

```
%LOCALAPPDATA%\Hranix\Hranix Shield\   # data\, .jwt_secret, .restic_password, config.env
```

(лог-каталог — отдельно, через `platformdirs.user_log_dir(...)`, тот же принцип, что и на
macOS/Linux — не проверялся живьём в этой сессии, т.к. живого Windows-запуска не было).

Формат `config.env` — тот же `KEY=VALUE`, что и в macOS/Linux README:

WAZUH_API_PASSWORD=<из infra/security/wazuh/.env>

## Кириллица в трее — честный открытый риск, не игнорируется

`infi.systray==0.1.12.1` использует ANSI-варианты Win32 API (`RegisterWindowMessageA`,
`InsertMenuItemA` и т.п. — не `...W`/Unicode-варианты, проверено чтением
`infi/systray/win32_adapter.py`) и свою обёртку `encode_for_locale()`
(`text.encode(locale.getpreferredencoding(), 'ignore')`) для кодирования любого текста перед
передачей в API. Подписи меню этого продукта — кириллические ("Открыть панель"/"Выход", RU-first
продукт, см. CLAUDE.md). На русской локали Windows это должно работать (кодовая страница cp1251
понимает кириллицу), но `windows-latest`-раннер по умолчанию — **английская локаль (en-US)**, чья
типичная кодировка (`cp1252`) **не содержит кириллических символов вообще**.

С `errors='ignore'` это не бросает исключение — незакодируемые символы молча отбрасываются, то есть
вероятный реальный эффект — **пустые/обрезанные подписи меню на английской локали**, не видимая
«кракозябра» (mojibake) и не падение.

Что реально проверяется (`test/check_tray_locale.py`, запускается воркфлоу до сборки):

1. **Не падает ли** конструирование/запуск `SysTrayIcon` с этими самыми кириллическими
   `menu_options` под реальной локалью раннера — единственное, что дымовой тест физически может
   проверить неинтерактивно (никакой headless CI-раннер не может синтетически кликнуть правой
   кнопкой по иконке в трее, чтобы открыть само меню — `TrackPopupMenu` модальный и заблокировал бы
   шаг навсегда в ожидании клика, поэтому скрипт **сознательно не вызывает** `_show_menu()`).
2. **Что реально делает `encode_for_locale()`** с точными кириллическими подписями под локалью
   раннера — напрямую, без риска зависания: кодирует строку, декодирует обратно, сравнивает с
   оригиналом, печатает результат. Это не падает по построению воркфлоу (несовпадение —
   логируется, не проваливает сборку) — реальный, заранее известный пробел в дизайне библиотеки не
   повод ронять сборку, но и не повод скрывать находку.

**Визуальная корректность кириллицы в самой иконке трея НЕ проверена** — нужен реальный человек,
смотрящий на реальный Windows-экран (правый клик по иконке, что показывает меню). Ни эта сессия, ни
CI не могут это подтвердить — честно зафиксировано как открытый пробел, не как «работает».

## Автозапуск при входе в Windows

Инсталлятор предлагает необязательный чекбокс "Запускать Hranix Shield при входе в Windows"
(`[Tasks]`'s `startupicon`, снят по умолчанию) — при выборе создаёт ярлык в
`{userstartup}` (`shell:startup`, per-user, без прав администратора). Не входит в жёсткий DoD (см.
план-спецификацию: "автозапуск... опционально"), но предложен, как и просил архитектор.

## A-25: официальный агент Wazuh (GPLv2) — опциональный `[Run]`-шаг

Тот же архитектурный разрыв, что решают A-20 (macOS)/A-22 (Linux): консоль «Журналы ОС» видит
файлы только Manager-контейнера (`infra/security/wazuh/docker-compose.yml`'s Decision #2), не
реальный хост нативной установки. `installer.iss` теперь предлагает необязательный чекбокс
«Установить агент Wazuh...» (`[Tasks]`'s `wazuhagent`, снят по умолчанию — тот же принцип, что и
`startupicon` выше: ничего постоянное/системное не ставится без явного согласия). При выборе —
`[Run]`'s `msiexec.exe /i ... /qn WAZUH_MANAGER="127.0.0.1" WAZUH_REGISTRATION_SERVER="127.0.0.1"`
(официальные MSI-параметры, см. documentation.wazuh.com, сверено 2026-07-18) молча ставит и
энролит агент против этой же машины (`infra/security/wazuh/docker-compose.yml`'s Decision #3,
2026-07-18 — порты 1514/1515 теперь опубликованы на `127.0.0.1`).

MSI **не хранится в git** — `.github/workflows/windows-build.yml` скачивает его с
`packages.wazuh.com` перед компиляцией `.iss` (см. `.gitignore`'s `packaging/windows/vendor/`),
версия зафиксирована на `4.14.6` — та же версия, что образ Manager'а
(`wazuh/wazuh-manager:4.14.6`) и macOS-агент (`packaging/macos/wazuh_agent_setup.py`'s
`AGENT_VERSION`) — Wazuh сам рекомендует совпадение версий агент/manager.

**Честный, не скрытый пробел (принцип 7):** в отличие от macOS (`wazuh_agent_setup.py`)/Linux
(`debian/postinst`), этот Windows-путь **не** правит собственный `ossec.conf` агента (`C:\Program
Files (x86)\ossec-agent\ossec.conf`), чтобы направить `<syscheck><directories>` на реальный
platformdirs-каталог данных (`%LOCALAPPDATA%\Hranix\Hranix Shield`) — такая правка потребовала бы
встроенного PowerShell-скрипта в `[Run]`/Pascal Script в `[Code]`, ни то ни другое не проверено
живьём в этой сессии (нет Windows-машины), и рисковать неверифицированной правкой чужого
конфиг-файла на реальной машине пользователя хуже, чем честно оставить это следующим шагом —
задокументировано как открытый пробел в `installer.iss`'s собственном комментарии, не молча
пропущено.

CI (`.github/workflows/windows-build.yml`) явно выбирает `wazuhagent`-задачу через ISCC's
`/TASKS="wazuhagent"` (чекбокс снят по умолчанию для реального пользователя, но этот CI-прогон
должен реально проверить именно этот новый шаг, а не молча его пропустить) и проверяет, что после
установки существует реальная Windows-служба `WazuhSvc` (`Get-Service WazuhSvc`) — но **не**
проверяет, что энролмент против реального Manager'а успешен: у `windows-latest`-раннера физически
нет маршрута к `infra/security/wazuh/docker-compose.yml` (тот контейнер существует только на
машине разработчика) — залогировано, не проверено как факт (принцип 8).

## SmartScreen: «незнакомое приложение»

Установщик и сам `.exe` **не подписаны** (Authenticode code signing — осознанно вне скоупа Фазы 0,
то же решение, что уже принято для macOS-нотаризации и GPG-подписи Linux `.deb`-репозитория).
Windows SmartScreen покажет предупреждение «Windows защитила ваш компьютер» при первом запуске
неподписанного `.exe`/установщика — то же трение, что Gatekeeper даёт на macOS. Обход стандартный:
«Дополнительно» → «Выполнить в любом случае». Не проверено живьём в этой сессии (нет Windows-машины
с реальным SmartScreen для наблюдения) — задокументировано по документированному поведению Windows,
не по факту.

### Примечание к таблице: почему `pystray` больше не в ней

См. "Замена библиотеки трея" выше для полной истории/обоснования — коротко: `pystray==0.19.5`
(LGPLv3) заменён на `infi.systray==0.1.12.1` (BSD-3-Clause) по решению пользователя, после того как
разработчик поднял лицензионную находку архитектору. `pystray`'s LGPL-обоснование, которое было в
предыдущей версии этого README, больше не актуально (осталось только в истории коммитов) — не
повторяется здесь во избежание путаницы с обоснованием для уже не используемой зависимости.

`infi.systray`'s собственный код (`infi/systray/win32_adapter.py`) использует только `ctypes`/
`ctypes.wintypes` (стандартная библиотека) — **`pywin32` не требуется**, проверено чтением
исходника пакета на PyPI, не предположено. Пакет также объявляет `Requires-Dist: setuptools` в
своих метаданных, но ничего в его исходном коде реально не импортирует `setuptools`/`pkg_resources`
(проверено `grep`) — вероятно, унаследованный артефакт `setup.py`-шаблона, не реальная зависимость
для сборки.

## DoD — честно, по каждому пункту отдельно (принцип 8)

### 1. «Код написан аккуратно, по документации» — ДА, но НЕ проверено сборкой

`hranix_shield_tray.py`, `hranix-shield.spec`, `installer.iss` написаны по образцу
`packaging/macos/`/`packaging/linux/` (тот же `sys.path`-guard, та же структура `.spec`, тот же
`launcher.py` без изменений) и по документации `infi.systray`/PyInstaller/Inno Setup — **не
гарантированно рабочий с первого раза** (нет способа проверить локально на macOS): `pyinstaller`
физически не соберёт Windows-бинарник здесь, `ISCC.exe` физически не запустится здесь. Логика
рисования иконки (тот же щит+"H", теперь сохраняемый в `.ico`) проверена изолированно — функция
рисования скопирована во временный venv с установленным `Pillow==12.3.0` и реально выполнена
(macOS, не Windows, но `PIL.Image`/`ImageDraw`/ICO-плагин кросс-платформенны), результат —
сохранённый `.ico`-файл без исключений. Сама интеграция с `infi.systray.SysTrayIcon`
(win32-специфичный код, `ctypes.windll...`) физически не может быть исполнена на macOS —
`infi/systray/win32_adapter.py` не импортируется вне Windows вообще.

### 2. `.github/workflows/windows-build.yml` — синтаксически корректен, ПРОВЕРЕНО

- `python3 -c "import yaml; yaml.safe_load(open(...))"` — парсится без ошибок.
- `actionlint` (установлен локально через `brew install actionlint` в этой сессии, версия
  1.7.12) — **ноль замечаний** по этому файлу (включая шаг с проверкой кириллицы в трее).
- `py_compile` на `hranix_shield_tray.py` и `test/check_tray_locale.py` — синтаксис корректен
  (импорты `infi.systray`/`PIL` не проверялись этим — `py_compile` не исполняет код, и
  `infi.systray` физически не импортируется на macOS в принципе).

### 3. Реальный прогон на `windows-latest` — НЕ ПРОИЗОШЁЛ в этой сессии

Нет доступа к GitHub Actions отсюда. **Не утверждается, что CI «зелёный»** — воркфлоу написан и
синтаксически провалидирован, но ни разу не выполнялся. Первый реальный прогон — когда архитектор
запушит этот код в GitHub. До этого момента ничего в этом каталоге не должно называться
«работает», только «написано и обосновано».

### 4. «Видит настоящий хост» — НЕ ПОДТВЕРЖДЕНО в этой сессии (будет частично подтверждаемо в CI)

Не проверено здесь вообще (нет Windows-машины). Когда воркфлоу реально выполнится, шаг 10 (сверка с
`netsh`) даст РЕАЛЬНОЕ доказательство на настоящей Windows ОС `windows-latest`-раннера — не
контейнер, как в Docker-развёртывании продукта. Раннер сам по себе — тоже не буквально «ноутбук
пользователя» (та же оговорка, что план-спецификация делает и для Linux-контейнера A-22), но это
уже настоящее Windows-ядро с настоящим Windows Defender Firewall, качественно другой уровень
доказательства, чем что-либо доступное внутри Docker.

### 5. Regression-сьют — ЗЕЛЁНЫЙ

`server/venv/bin/python -m pytest -q` (запущен из этого worktree против уже существующего dev-venv
основного чекаута): **508 passed, 11 skipped**, без единой правки внутри существующих тестов. A-21
не трогает `server/app/`, `server/launcher.py` или `server/app/config.py` — только добавляет

### 6. (A-24) osquery вшит в спеку/CI — написано и синтаксически провалидировано, реальный прогон НЕ произошёл

`hranix-shield.spec`'s новая `VENDOR_OSQUERYI`-проверка + `datas=[...]`-строка, и
`.github/workflows/windows-build.yml`'s новые шаги "Vendor osquery" и "Compare the
"Сеть"/"Вирусная активность" консоли..." — написаны по документированному поведению
`msiexec /a` (административная установка MSI) и проверены синтаксически (`actionlint` — ноль
замечаний по обновлённому файлу, включая оба новых шага; `python3 -c "import yaml;
yaml.safe_load(...)"` — парсится). MSI-инструмент выбора имени файла `osqueryi.exe` внутри
пакета (отдельный PE32+-файл, не переименование `osqueryd.exe`, в отличие от macOS/Linux)
подтверждён на этой macOS-машине через независимый opensource-инструмент `msitools`'
`msiextract` (установлен через `brew install msitools`, версия 0.106) — это НЕ то же самое, что
реальный `msiexec.exe` на настоящей Windows, но даёт разумную уверенность, что
`Get-ChildItem -Recurse -Filter osqueryi.exe`-подход в воркфлоу найдёт файл независимо от
точного имени промежуточного каталога административной установки. **Ни один из новых Windows-
шагов не выполнялся на реальной машине/CI в этой сессии** — тот же честный лимит, что и у всего
остального в этом каталоге (см. пункт 3 выше). Первое реальное подтверждение — когда архитектор
запушит этот код и посмотрит на реальный прогон в Actions.

## Известные ограничения / что честно не сделано

- Ничего в этом каталоге не собиралось и не запускалось на реальной Windows-машине или CI в этой
  сессии — см. DoD выше.
- **Визуальная корректность кириллицы в реальном тray-меню — НЕ проверена** (см. "Кириллица в
  трее" выше) — только неинтерактивная, безопасная (не вызывающая модальный `TrackPopupMenu`)
  проверка кодирования строк и факта отсутствия исключения при запуске.
- Code signing (Authenticode)/SmartScreen-репутация — не в скоупе (как и на macOS/Linux).
- Полноценный Windows NT-сервис (`pywin32`) — сознательно не сделан (архитекторское решение,
  см. выше), не переоткрывалось.
- Onedir vs onefile — не переизмерено эмпирически для Windows (только унаследовано от измерения
  A-20 на macOS) — см. `hranix-shield.spec`'s собственный комментарий.
- Graceful shutdown (SIGTERM-эквивалент) в CI смоук-тесте — не проверялся, только жёсткий
  `Stop-Process -Force` как teardown (см. воркфлоу, шаг 11).
- Автозапуск при входе (`{userstartup}`) — написан по документации Inno Setup, не проверен живьём.
- Дублирующийся пункт меню "Quit" (английский, захардкожен `infi.systray`'s собственным кодом)
  рядом с "Выход" — см. "Замена библиотеки трея" выше, косметическая особенность библиотеки, не
  устранимая без форка/патча зависимости.
